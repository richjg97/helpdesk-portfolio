01

ipconfig — Check Network Configuration

First step any Level 1 analyst runs when a user reports a connectivity issue. ipconfig reveals the current IP address, subnet mask, and default gateway — immediately showing whether the machine has a valid network configuration.

Command Prompt — helpdesk@WINDOWS10-LAB
C:\Users\helpdesk> ipconfig
Windows IP Configuration
 
Ethernet adapter Ethernet:
  Connection-specific DNS Suffix . : localdomain
  IPv4 Address. . . . . . . . . . : 10.0.2.15
  Subnet Mask . . . . . . . . . . : 255.255.255.0
  Default Gateway . . . . . . . . : 10.0.2.2

What this tells me

IPv4 address and default gateway are both present — healthy configuration. A missing gateway would mean the machine can't reach anything outside the local network, which would be the immediate root cause of a "can't access internet" complaint.

Real help desk scenario

User calls: "I can't get on the internet." Run ipconfig first. No IPv4 or no default gateway = root cause found before asking another question.

02

ping 8.8.8.8 — Test Internet Connectivity

With a valid IP confirmed, the next step is testing whether the machine can actually reach the internet. Pinging Google's public DNS server by IP address — not by name — isolates the test to raw connectivity and rules out DNS as the variable.

Command Prompt — helpdesk@WINDOWS10-LAB
C:\Users\helpdesk> ping 8.8.8.8
Pinging 8.8.8.8 with 32 bytes of data:
Reply from 8.8.8.8: bytes=32 time=10ms TTL=255
Reply from 8.8.8.8: bytes=32 time=21ms TTL=255
Reply from 8.8.8.8: bytes=32 time=7ms TTL=255
Reply from 8.8.8.8: bytes=32 time=11ms TTL=255
 
Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)
Average round trip time: 12ms

What this tells me

0% packet loss and 12ms average confirms clean internet connectivity. If ping had failed here, the problem would be network-level — wrong gateway, ISP issue, or firewall. Since it succeeded, any remaining issue is DNS or application-specific.

Real help desk scenario

User says "websites won't load." If ping 8.8.8.8 succeeds but ping google.com fails — internet is fine, DNS is broken. That tells you exactly which fix to apply: flushdns.

03

tracert 8.8.8.8 — Trace the Network Route

tracert shows every hop traffic takes between the machine and the destination. When a connection is intermittent or slow, tracert pinpoints exactly where the problem occurs — local network, ISP, or the destination server.

Command Prompt — helpdesk@WINDOWS10-LAB
C:\Users\helpdesk> tracert 8.8.8.8
Tracing route to dns.google [8.8.8.8] over a maximum of 30 hops:
 
  1   13 ms   7 ms   8 ms   dns.google [8.8.8.8]
 
Trace complete.

What this tells me

1 hop, all under 15ms — direct connection, nothing timing out. In a real problem scenario, timeouts (* * *) at hop 2 or 3 point to a router or ISP issue. A timeout only at the final hop means the destination is blocking the probe — not a local problem.

04

ipconfig /flushdns — Clear DNS Cache

One of the most common Level 1 fixes. When a user can ping an IP address directly but websites won't load by name, the DNS cache is usually corrupted or outdated. Flushing it forces Windows to request fresh DNS records.

Command Prompt (Admin) — helpdesk@WINDOWS10-LAB
C:\Users\helpdesk> ipconfig /flushdns
Windows IP Configuration
 
Successfully flushed the DNS Resolver Cache.

What this tells me

DNS cache cleared. After this, the user should be able to load websites again if DNS was the cause. Takes 5 seconds and resolves a large percentage of "some sites work, others don't" complaints.

Real help desk scenario

"I can connect to some sites but not others, and it worked fine yesterday." Classic stale DNS. flushdns is the first fix to try — fast, harmless, and effective.

05

ipconfig /release + /renew — Reset IP Address

When a user shows no valid IP or has an IP conflict, releasing and renewing forces the network adapter to request a fresh IP lease from the DHCP server. This resolves IP conflicts, APIPA addresses, and stale DHCP leases.

Command Prompt (Admin) — helpdesk@WINDOWS10-LAB
C:\Users\helpdesk> ipconfig /release
Ethernet adapter Ethernet:
  IPv4 Address. . . : [released]
  Default Gateway . : [cleared]
 
C:\Users\helpdesk> ipconfig /renew
Ethernet adapter Ethernet:
  IPv4 Address. . . : 10.0.2.15
  Subnet Mask . . . : 255.255.255.0
  Default Gateway . : 10.0.2.2

What this tells me

IP successfully released and a fresh address obtained from DHCP. Machine is fully reconnected. This is the go-to fix for 169.254.x.x APIPA addresses — which appear when a machine can't reach the DHCP server to get a real IP.

Real help desk scenario

"My IP shows 169.254.x.x and nothing works." That's APIPA — the machine couldn't get a DHCP lease. Release, renew, check DHCP server connectivity, escalate if unresolved.
